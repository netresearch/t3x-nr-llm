# A language model revises a DeepL translation on request

A caller that translates through DeepL can ask, in the same call, for a language model to revise the result for fluency, terminology and tone. The option is off by default; a caller that does not set it sees no change (ADR-233).

## Required behavior

1. `TranslationOptions::withPolish(bool $enabled = true, ?string $instruction = null)` asks for the revision; `isPolishEnabled()` and `getPolishInstruction()` read it. It is not a constructor parameter and not part of `toArray()`.
2. `translateWithTranslator()` and `translateBatchWithTranslator()` revise the result when the option is set and the translator that ran is not the LLM translator. After the LLM translator nothing is called and `metadata['polish']` says `applied: false, reason: llm_translator`.
3. The revision is one `LlmServiceManager::chat()` call on the default configuration or the pinned provider and model, with the caller's backend user and planned cost for the budget pre-flight. Its chat row carries tokens and cost with the caller's extension and operation; a `translation_polish` usage row records the revised characters with the caller's extension. The `translation_polish` row never counts as a request. After DeepL, which writes a counting request row for the same backend user before the revision, the chat call does not count either and its pre-flight leaves the request out of the user's per-day and per-month request limits (`ChatOptions::withRequestAlreadyCounted()`, `BudgetMiddleware::METADATA_REQUEST_ALREADY_COUNTED`, `BudgetService::checkWithoutNewRequest()`); the configuration's per-day request cap still counts it, because DeepL's row carries no configuration, and token and cost limits apply. After any other non-LLM translator the chat call is an ordinary request with an ordinary pre-flight. Calls that only suppress the request count keep their check.
4. The prompt passes source text and translation, and asks to keep meaning, formality, tags, placeholders and glossary target terms, and to return only the text. The caller's instruction is added to the system message; it is caller-controlled and must not carry editor input.
5. The first translation is returned unchanged, with `metadata['polish']['reason']`, when the call fails or the budget refuses it, the answer is empty or cut off, it starts with a code fence, a preamble word or a first line ending in a colon that the first translation does not start with, it has more non-empty lines, its tags and HTML comments (normalised, with attributes, in document order) or placeholders (`{name}`, printf conversions; as a multiset) differ from the first translation's, anything after the call throws, a glossary target term occurs less often, or no polisher is wired. The translation itself never fails because of the revision.
6. `TranslatorResult::isPolished()` is true only for an applied revision; `translator` stays the first-pass translator.
7. With the translation cache on, a requested revision is part of the key (instruction and the revising model's fingerprint), a result whose revision was not applied is not stored, and keys without a revision do not change.
8. The API surface change is additive: three methods on `TranslationOptions`, one on `TranslatorResult`, two on `ChatOptions`, and an optional trailing constructor parameter of the service.
9. The site glossary and the backend user are resolved once per call and once per batch.

## Not done

No configuration of its own for the revision (a configuration named with `withConfiguration()` selects the translator only), no guard for ICU plural blocks, `{{ name }}` with spaces, `%%`, HTML entities or the extent of a link, no revision on `translate()` or `translateForConfiguration()` (they translate with a language model already), no meaning check beyond what the prompt asks, no new translator in the registry, no change to `TranslationResult`.

## Tests

- Unit `TranslationServicePolishTest` (50 cases): revision applied; nothing called without the option; skipped after the LLM translator, also in a batch; fallback on a dropped tag, an altered attribute, crossed nesting, swapped link targets, a dropped comment, a dropped or altered placeholder, an empty answer, a code fence, a one-line, an English and a German preamble, an introducing line without a keyword, a trailing note, a cut-off answer, a budget refusal, a failed call, an exception after the answer arrived, a dropped glossary term (explicit and site glossary), a missing polisher; an empty or cut-off first translation not revised; moved tags and placeholders accepted; `<br>`/`<br />`, tag case, quote style and comment whitespace accepted; a preamble-like start the first translation shares accepted; "Here isolated …" accepted; a surviving glossary term lets the revision apply; an empty glossary target ignored; formality and instruction in the prompt; log levels (budget and provider failures as warnings, anything else as an error) with the exception; usage row `translation_polish` with extension and user, not a request; chat call marked as already counted after DeepL and an ordinary request after another translator; the site glossary resolved once per call and once per batch; batch revised per text; cache key differs with and without revision, per instruction and per revising model; not cached when the revising model cannot be told; a fallback is not cached.
- Unit `BudgetMiddlewareCountedRequestTest` (8 cases, real middleware and budget service): at N of N requests used after the translation, the revision is allowed in the daily and in the monthly window; a call not marked is refused in both; a call that only suppresses the request count is refused as before; an exhausted cost limit still refuses the revision; a configuration's per-day request cap still refuses it; another budget service implementation is asked `check()`.
- Unit `ApiSurfaceSnapshotTest`: the snapshot holds the new methods and the widened service constructor.
- Functional `TranslationServicePolisherWiringTest`: the container hands the service its polisher; overriding the argument with null fails it.
- Mutations run in the last round, each restored from a copy and checked by sha256, each detected (a failed assertion, or for six of them a test error whose exception was read in the log and is the one the test rules out): incomplete first translation and its truncated half; empty; truncated; code fence; preamble, its draft exemption and its word boundary; introducing line; added lines; tag guard, tag order turned into a multiset, tags not normalised, comments left out, tag name case kept, quote style kept, comment whitespace kept, the attribute pattern keeping `/`; placeholder guard and placeholders turned into an ordered list; glossary guard, `<` to `<=`, empty glossary target; the catch narrowed to provider and budget exceptions; budget reason; log level always warning, provider failure as error, exception object not logged; usage operation; polish row as a request; already-counted always set and never set in the polisher and in the service; LLM skip; polish, instruction and model in the cache key; null key cached; fallback stored; site-glossary fallback; the glossary resolved again in a batch; the budget service's request-free check, its `newRequests` ignored, the monthly window counting, the configuration cap skipping the request; the middleware ignoring the flag or its value; the metadata factory dropping the key. One earlier mutant, a trailing `/` kept by the tag regex, was equivalent: the attribute pattern already skips `/`, so the redundant regex part was removed and the attribute pattern mutated instead.
