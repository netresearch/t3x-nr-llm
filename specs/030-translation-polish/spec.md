# A language model revises a DeepL translation on request

A caller that translates through DeepL can ask, in the same call, for a language model to revise the result for fluency, terminology and tone. The option is off by default; a caller that does not set it sees no change (ADR-233).

## Required behavior

1. `TranslationOptions::withPolish(bool $enabled = true, ?string $instruction = null)` asks for the revision; `isPolishEnabled()` and `getPolishInstruction()` read it. It is not a constructor parameter and not part of `toArray()`.
2. `translateWithTranslator()` and `translateBatchWithTranslator()` revise the result when the option is set and the translator that ran is not the LLM translator. After the LLM translator nothing is called and `metadata['polish']` says `applied: false, reason: llm_translator`.
3. The revision is one `LlmServiceManager::chat()` call on the default configuration or the pinned provider and model, and an ordinary request: its budget pre-flight runs with the caller's backend user and planned cost, and its chat row counts as a request and carries tokens and cost with the caller's extension and operation. A polished translation uses two requests. At a user's or a configuration's request limit the revision is refused and the first translation is returned with `reason: budget_refused`. A `translation_polish` usage row records the revised characters with the caller's extension and does not count as a request.
4. The prompt passes source text and translation, and asks to keep meaning, formality, tags, placeholders and glossary target terms, and to return only the text. The caller's instruction is added to the system message; it is caller-controlled and must not carry editor input.
5. The first translation is returned unchanged, with `metadata['polish']['reason']`, when the call fails or the budget refuses it, the answer is empty or cut off, it starts with a code fence, a preamble word or a first line ending in a colon that the first translation does not start with, it has more non-empty lines (line breaks between tags and after a `<br>` not counted), its tags and HTML comments (normalised, with attributes, in document order) or placeholders (`{name}`, printf conversions; as a multiset) differ from the first translation's, anything after the call throws, a glossary target term occurs less often, or no polisher is wired. The translation itself never fails because of the revision.
6. `TranslatorResult::isPolished()` is true only for an applied revision; `translator` stays the first-pass translator.
7. With the translation cache on, a requested revision is part of the key (instruction and the revising model's fingerprint), a result whose revision was not applied is not stored, and keys without a revision do not change.
8. The API surface change is additive: three methods on `TranslationOptions`, one on `TranslatorResult`, and an optional trailing constructor parameter of the service.
9. The site glossary and the backend user are resolved once per call and once per batch.

## Not done

No configuration of its own for the revision (a configuration named with `withConfiguration()` selects the translator only), no guard for ICU plural blocks, `{{ name }}` with spaces, `%%`, HTML entities, the extent of a link or a label on the same line outside the tags, no tolerance for an attribute value rewritten without changing its meaning (`&amp;` to `&`), no revision on `translate()` or `translateForConfiguration()` (they translate with a language model already), no meaning check beyond what the prompt asks, no new translator in the registry, no change to `TranslationResult`.

## Tests

- Unit `TranslationServicePolishTest` (56 cases): revision applied; nothing called without the option; skipped after the LLM translator, also in a batch; fallback on a dropped tag, an altered attribute, an `&amp;` rewritten in an `href`, crossed nesting, swapped link targets, a dropped comment, a dropped or altered placeholder, an empty answer, a code fence, a one-line, an English and a German preamble, an introducing line without a keyword, a note after the last closing tag, a trailing note, a cut-off answer, a budget refusal, a failed call, an exception after the answer arrived, a dropped glossary term (explicit and site glossary), a missing polisher; an empty or cut-off first translation not revised; moved tags and placeholders accepted; `<br>`/`<br />`, tag case, quote style, comment whitespace, a list laid out on lines and a line break after a `<br>` accepted; a preamble-like start and an introducing first line the first translation shares accepted; "Here isolated …" accepted; a same-line label outside the tags not caught (accepted limit); a surviving glossary term lets the revision apply; an empty glossary target ignored; formality and instruction in the prompt; log levels (budget and provider failures as warnings, anything else as an error) with the exception, also for a failed usage row, which keeps the revision; usage row `translation_polish` with extension and user, not a request; chat call without request-count suppression; the site glossary resolved once per call and once per batch; batch revised per text; cache key differs with and without revision, per instruction and per revising model; not cached when the revising model cannot be told; a fallback is not cached.
- Unit `TranslationPolishAccountingTest` (4 cases; the chat call runs through the real `BudgetMiddleware`, `BudgetService` and `UsageMiddleware`, and the usage windows sum the recorded rows as the SQL does): a polished translation adds two counted requests, one of them the chat row, and a non-counting `translation_polish` row; with N−1 of N requests used, DeepL brings it to N and the revision is refused with `budget_refused`, DeepL's text returned and no further row written; the revision's chat row raises the configuration's request count by one; at the configuration's cap the revision is refused.
- Unit `ApiSurfaceSnapshotTest`: the snapshot holds the new methods and the widened service constructor.
- Functional `TranslationServicePolisherWiringTest`: the container hands the service its polisher; overriding the argument with null fails it.
- Mutations of the round that made the revision an ordinary request, each restored from a copy and checked by sha256 and each detected by a failed assertion against the 60 tests above: the layout-break removal as a whole, between tags and after a `<br>`; the added-lines guard; the introducing-line draft exemption; request-count suppression on the revision's chat call; the `translation_polish` row counting as a request; the exception object left out of the usage-failure log; the usage failure no longer caught; the budget reason. The guards kept from the earlier rounds (empty, truncated, code fence, preamble, tags, placeholders, glossary, catch-all, log levels, cache key, site glossary) were mutated in those rounds; the pull request lists them.
