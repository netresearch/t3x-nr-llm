# Evaluation results identify the model that generated them — ADR-220

The actual defect is reproducible through EvaluationService, the SQLite result repository, EvaluationQualityScoreProvider and CandidateRanker: a primary failure and a fallback success are stored as the fallback's aggregate quality. This specification corrects that attribution while retaining the existing grading protocol.

## Required behavior

1. Distinguish three facts: the configured DB provider-instance identifier (for example `internal-openai`), the actual outbound model alias (for example `gpt-4o`) and the response's reported model (for example `gpt-4o-2024-11-20`). `CompletionResponse.provider` is the adapter key (for example `openai`), not a DB provider instance. It cannot establish generator eligibility.
2. The successful configuration-driven chat/completion pipeline terminal records a reserved additive `CompletionResponse.metadata['nr_llm_serving_generator']` value with version one, the DB provider-instance identifier of that terminal's resolved model, the model alias actually passed to the adapter, and the response's reported model. Build it only after the adapter returns successfully, overriding any adapter-supplied value for that reserved key. Use the actual fallback terminal's resolution and final callOptions, including an actual per-call model override; do not use the originally requested/default/primary configuration as serving evidence. Adapter-only ad-hoc calls without a DB instance have no eligible record. The response constructor and every other response field stay unchanged. Cache/idempotency replay and guardrail content reconstruction preserve the original served record, rather than relabeling a cached response with today's request.
3. PromptEvaluation retains this optional trailing internal provenance plus the reported adapter key alongside grade and latency; old constructors default to unknown. A run has one eligible generator only when every prompt's verified record has the same provider instance, outbound alias and reported model. Unknown, mixed, invalid or empty results produce an empty run-level model and no eligible generator provenance. A homogeneous run's model key is the successful terminal's outbound alias; the reported model remains explicit in provenance. A requested model option alone never manufactures evidence. Never use the final response as the whole run's identity.
4. Preserve all prompt grades and aggregate rates for mixed and unknown runs. Grader identity remains a separate dimension: answers from different generator models may share the same deterministic yardstick. `sharesOneYardstick()` keeps that meaning.
5. Store a content-free version-one generator-provenance record in a dedicated `generator_provenance` result column, separately from privacy-filtered details. Its exact JSON shape is `{version: 1, providerIdentifier: string, modelId: string, reportedModelId: string}`; the response metadata uses this same shape. Provider instance IDs are 1..100 ASCII letters/digits/underscore/dot/hyphen; both model identifiers are 1..150 ASCII letters/digits/underscore/dot/hyphen/slash/colon/at-sign/plus, excluding URL schemes. This follows the existing model_id column bound. Invalid/unbounded identifiers produce an unknown eligible identity, without discarding grades. Mixed/unknown runs have no eligible record. Empty legacy values are unverified. Parse metadata defensively: absent, malformed, extra/missing fields, unsupported-version or row-inconsistent values cannot prove eligibility. `modelId` must agree with the row's model identity. Do not reuse retrieval_provenance for a generator.
6. Metadata privacy removes the entire details payload but preserves the content-free generator identity, so a homogeneous evaluation remains usable as a quality signal at the default privacy level. Full privacy preserves reported per-prompt identities. No raw completion content, options, endpoint or credentials are added. Existing retention deletes aggregates, provenance and details together.
7. A run with no verified single generator identity cannot become a generator-specific regression baseline or quality signal. The CLI records it and explicitly skips that comparison; without the strict flag it succeeds as a measurement, with `--fail-on-regression` it fails as an unverified gate. A previous legacy, unknown, wrong-provider or unsupported-version row must not become the baseline of a new verified run. A first verified run is a new baseline.
8. Core routing scopes quality to provider and model. Add optional provider/model quality-provider and verified-generator repository capability interfaces alongside the existing interfaces; existing implementations acquire no required members. CandidateRanker and QualityAwareModelSelector use the capability when available and preserve the existing model-ID contract for custom providers that implement only the old interface. EvaluationQualityScoreProvider uses only verified repository reads; an old custom repository without the capability yields unknown for this core adapter.
9. The existing unscoped repository quality read excludes unverified rows and yields unknown when the same model ID has verified results from several providers. A scoped read averages the latest eligible run per set for its provider/model/grader, preserving measured zero as zero. Legacy aggregates remain available through ordinary history reads; do not backfill unverifiable provenance or delete those rows.

The additive capabilities are `ProviderModelQualityScoreProviderInterface::getQualityScoreForProviderModel(string $providerId, string $modelId): ?float` and `GeneratorEvaluationResultRepositoryInterface`, which extends the unchanged repository interface with `meanQualityScoreForProviderModel(string $providerId, string $modelId, string $grader): ?float` and `findLatestForGenerator(string $setIdentifier, string $providerId, string $modelId, string $reportedModelId, string $grader): ?EvaluationResultSummary`. The baseline read filters verified rows by all five dimensions before choosing the latest row: a newer run reporting a different snapshot cannot mask an earlier matching baseline. The unchanged historical `findLatest` and `findRecent` reads still expose legacy rows. New internal prompt/set/summary DTOs carry trailing optional generator metadata. Registered optional capabilities are autowired to the same core implementations; no parallel store or evaluator is introduced.
10. A homogeneous run supports regression comparison and quality routing under the verified provider-instance/model-alias scope. Baselines additionally require the same reported model, so a changed reported snapshot does not silently become a regression on fixed weights. Requested/default model options remain request options until the actual successful terminal supplies evidence. Grader failures keep their existing separate handling. A provider-instance change with an unchanged adapter key/model alias is a different generator.
11. Existing constructors remain source compatible through trailing optional fields; the frozen `@api` declarations do not change. Detail snapshots gain additive internal metadata keys. Retrieval conversions keep their existing retriever identity and provenance; generator requirements apply to prompt completion runs.
12. Documentation explains generator identity versus grading identity, paid generation calls, and the existing measured-quality integration in ModelSelectionService. Old scores remain readable but cease contributing to core quality routing without verified provenance; re-evaluation restores an eligible measured signal. The database update and additive optional repository/provider capabilities are documented.

| Per-prompt response identities survive conversion without breaking old constructors | Unit PromptEvaluation/SetEvaluationResult tests |
| Mixed deterministic grading remains comparable as a grading protocol | Unit and functional: sharesOneYardstick remains true |
| Unknown/mixed runs are stored, not compared, and fail only the strict generator gate; verified first runs ignore legacy/wrong-provider baselines | Unit EvalRunCommandTest and functional repository scope tests |
| Baselines filter reported snapshots before choosing the latest row; a newer different snapshot cannot mask an older matching baseline | Functional repository ordering fixture and CLI comparison of the matching baseline |
| Mixed and legacy aggregate scores do not contaminate actual model routing; homogeneous scores still do, including measured zero | Functional EvaluationResultRepository -> EvaluationQualityScoreProvider -> CandidateRanker with SQLite |
| Identical model names at different providers do not share scores; unscoped ambiguity yields unknown | Functional scoped/unscoped repository and CandidateRanker tests |

| RST links, ADR index, API freeze, changelog and all required checks | Documentation renderer, existing API/ADR tests, make gate |
