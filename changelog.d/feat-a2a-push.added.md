- A2A push notifications in the server role (spec 051 stage 5b, ADR-285). While the new extension setting `a2a.server.push` is on, the agent card declares `pushNotifications`, and a client can register webhooks for its own tasks with `CreateTaskPushNotificationConfig`, `GetTaskPushNotificationConfig`, `ListTaskPushNotificationConfigs` and `DeleteTaskPushNotificationConfig`, or embed one in `SendMessage`. A webhook must be https and pass the address guard, with host lists of its own (`a2a.push.allowedHosts`, `a2a.push.deniedHosts`). The Bearer credential and the token are stored sealed and the credential is answered masked. Each task event writes one delivery job per config in the transaction that writes the event; `nrllm:a2a:poll` delivers them, never a request. A delivery is a `{"task": …}` `StreamResponse` with the credential in `Authorization`; 2xx acknowledges, timeouts, 429, 502 to 504 and redirects are retried up to eight times per config with a backoff that a newer event of the config continues, 401 and 403 pause the config, 404, 410 and a refused address stop it. One run of `nrllm:a2a:poll` claims no delivery after 30 seconds and takes at most 10 deliveries per client, the clients taking turns. Administrators see the configs and their state in the List module (`A2A Push Config`, root level).
