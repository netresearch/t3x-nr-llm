- A run can be bound to the scope of its assignment, and every write is checked against it (ADR-295, `Documentation/Administration/AssignmentScope.rst`). `AssignmentScope` names page subtrees (a page and a depth), single records, and optionally the tables and languages the run may write. A starter sets it on the acting identity with `AiActorContext::withAssignmentScope()`; it is stored with the run like the workspace, so a queued, suspended or resumed run keeps it, and nothing the assistant sends can widen it. Two new configuration settings, both off by default and changing nothing for an existing record: `require_assignment_scope` refuses every write of a run that has no scope, and `assignment_scope_max_depth` caps how far below a scoped page a run may write. The scope is checked twice. `RequireAssignmentScopeRule` reads what a write tool says it will touch (the new `ScopedWriteInterface`, implemented by all built-in write tools) before the approval card, and a DataHandler hook refuses, while a call runs, every write outside the scope, including those of a hook of the installation, the child records of an inline relation and the subpages a page delete takes along. A refused write is an error result that names what was refused, and the `tool_changes` step of the run carries a `refused` list. A tool that changes things outside TYPO3 (MCP, remote agents) and a write tool that states no targets are refused while a scope applies. A write that does not go through the DataHandler has the first check only. `AiActorContext::backendUser()` gains an optional trailing parameter, `ToolInvocationDecision` an optional `refusals`, `ObservedChangeSet` an optional `refused`.
